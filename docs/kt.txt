System Design

Changed file intake: ChangedFilesProvider normalizes CHANGED_FILES input → PlanRunner (triggered by --plan) feeds paths to PlanService.
Plan assembly: PlanService uses FileParsingStrategyFactory (one strategy per domain dir) + JsonModelMapper to deserialize JSON into models (SideFile, GeneralLedgerProfileFile, etc.). Special categories consult StateFileService for delete detection. Results are accumulated into PlanItems.
Ordering: PlanOrderingRuleEngine applies configured rules (see application.properties) to sort items before PlanWriter persists plan/masterplan.json.
Apply phase: PlanApplyService (run via --apply) reads the master plan through PlanReader, converts payloads, resolves the right PlanItemApplier, and delegates to the matching PlanItemActionService (e.g., GeneralLedgerProfileApiService) which currently logs the intended LUSID call. Each successful apply updates the persisted JSON stored in the Cosmos container `transaction_types_config` via StateFileService.
Supporting layers: FileLocationProperties wires directory names, JacksonConfiguration configures Jackson, tests cover models/ordering/state handling, and logging traces the lifecycle (PlanRunner logs, PlanApplyService errors, etc.).


Low-level design notes

Input layer: ChangedFilesProvider reads CHANGED_FILES; each path is normalized (PathUtils) and passed to PlanService.
Parsing & mapping:
PlanService consults FileParsingStrategyFactory (one bean per directory, e.g., SideFileParsingStrategy, GeneralLedgerProfileFileParsingStrategy).
Each strategy uses JsonModelMapper → this class applies custom parsing for structured lists (e.g., SideFile, AccountFile, AborFile, etc.) and falls back to Jackson for simple payloads.
Plan construction:
PlanService maps parsed payloads to PlanItems, comparing against the Cosmos container via StateFileService to emit CREATE/UPDATE/DELETE entries (special flows for list-based files scan for missing entries).
PlanOrderingRuleEngine sorts PlanItems using configured rules (PlanOrderingProperties + defaults that specify action order and optional transactionSequence sorting).
PlanWriter writes MasterPlan.
Apply phase:
PlanApplyService reads the master plan (PlanReader), converts payload nodes to typed requests, resolves PlanItemApplier by FileCategory, and calls PlanItemActionService (e.g., GeneralLedgerProfileApiService, PostingModuleApiService).
Each action logs the intended SDK call and then StateFileService updates the persisted JSON (write/delete logic per category).
State tracking: FileLocationProperties centralizes folder names; StateFileService handles tag-based filenames (key-scope.json) and ensures GeneralLedgerProfile files use glprofile folder.
